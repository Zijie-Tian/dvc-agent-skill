# DVC Agent Skill

Teach coding agents to drive **DVC** without bloating Git, forging hashes, or
breaking pipeline/cache contracts.

Official docs: https://doc.dvc.org/

## Mental model (always apply)

```text
Git  = code + metafiles (dvc.yaml, dvc.lock, *.dvc, params, metrics sources)
DVC  = content-addressed cache of bulk files + remote storage + pipeline runner
```

| Concern | Tool |
|---------|------|
| Source code, configs, small text | **Git** |
| Datasets, model weights, large binaries | **DVC** (`dvc add` / pipeline outs) |
| Which *version* of bulk data | Git commit of metafiles + `dvc checkout` / `dvc pull` |
| Reproducible transforms | `dvc.yaml` stages + `dvc repro` / `dvc exp` |
| Team / CI sharing of bulk objects | `dvc remote` + `dvc push` / `dvc pull` |

**Never** commit dataset blobs or model weights to Git if DVC is in use.
**Never** invent or hand-edit content hashes (`md5` in `*.dvc` / `dvc.lock`).

---

## Preflight checklist

Before any DVC work in a repo:

1. `git rev-parse --is-inside-work-tree` — must be a Git repo.
2. `command -v dvc && dvc version` — install if missing (prefer `pipx install "dvc[s3]"` or extras for the target remote).
3. Detect existing project: look for `.dvc/config`, `dvc.yaml`, `*.dvc`.
4. If uninitialized and user wants DVC: `dvc init` then commit `.dvc/` meta (not cache).
5. Prefer reading [project-layout](references/project-layout.md) once when orienting.

Optional quality-of-life:

```bash
dvc config core.autostage true   # auto git-add metafiles DVC touches
```

## Core workflows (decision tree)

### A. Track a static dataset or model artifact

Use when files are **inputs**, not regenerated by a pipeline stage.

```bash
dvc add path/to/data_or_model
git add path/to/data_or_model.dvc path/to/.gitignore   # dvc rewrites gitignore
git commit -m "Track <name> with DVC"
# after remote is configured:
dvc push
```

Rules:

- One logical artifact → one `dvc add` (file or directory).
- Do **not** `dvc add` paths that are already `outs` of a stage in `dvc.yaml`.
- After editing tracked bulk files: `dvc unprotect <path>` if read-only links, then edit, then `dvc add` again (or `dvc commit` if already listed).

### B. Build / run a pipeline

Use when data is **produced** by code (prep → train → eval).

```bash
# Prefer declarative stages
dvc stage add -n prepare \
  -d src/prepare.py -d data/raw \
  -o data/prepared \
  python src/prepare.py

dvc stage add -n train \
  -d src/train.py -d data/prepared -p train \
  -o models/model.pkl -M metrics/train.json \
  python src/train.py

dvc repro                 # run only what changed
dvc dag                   # visualize
git add dvc.yaml dvc.lock params.yaml metrics/
git commit -m "Add/update DVC pipeline"
dvc push
```

Rules:

- Stage `cmd` must be re-runnable and non-interactive.
- Declare **all** file deps with `-d` / `deps:`; params with `-p` / `params:`.
- Metrics usually `cache: false` (`-M`) so JSON lives in Git.
- After intentional stage edits, `dvc repro` (or `dvc repro <stage>`) then commit `dvc.lock`.
- Do not hand-merge lock hashes; re-run if conflict.

### C. Configure remotes and share data

```bash
dvc remote add -d storage s3://bucket/path   # or gs://, azure://, ssh://, local path
# secrets → config.local or env, NEVER commit:
dvc remote modify --local storage access_key_id ...
dvc push
dvc pull   # other machines / CI after git clone
```

Rules:

- Default remote: `-d` on `dvc remote add`.
- Cloud needs matching DVC extra (`dvc[s3]`, `dvc[gs]`, …).
- `dvc pull` after `git clone` / `git checkout` of new metafiles.
- Local-only secrets: `.dvc/config.local` (gitignored).

### D. Experiments (`dvc exp`)

Use for hyperparameter / code trials without polluting main branch history.

```bash
dvc exp run -S train.lr=0.01
dvc exp show
dvc exp apply <exp_id>    # bring into workspace when chosen
# or dvc exp branch <exp_id> <branch>
```

Rules:

- Params live in `params.yaml` (or declared param files); change via `-S` or file edit + `exp run`.
- Compare with `dvc exp show` / `dvc metrics show` / `dvc plots diff`.
- Promote winners with `exp apply` + normal git commit of resulting metafiles.

## Hard rules (pitfalls agents must avoid)

1. **No forged hashes** — never invent `md5`/`etag` in `*.dvc` or `dvc.lock`.
2. **No double-tracking** — pipeline `outs` are owned by stages; do not also `dvc add` them.
3. **No bulk files in Git** — if `dvc add` updated `.gitignore`, keep those ignores.
4. **No secrets in committed config** — remotes credentials only in `config.local` or env.
5. **Respect cache links** — workspace may be hardlink/symlink/read-only; `dvc unprotect` before in-place edit.
6. **Commit meta, push data** — after tracking/repro: `git commit` metafiles **and** `dvc push` when a remote exists.
7. **Checkout pair** — `git checkout` alone does not materialize bulk data; follow with `dvc checkout` or `dvc pull`.
8. **Do not delete `.dvc/cache` casually** — recover with `dvc pull` if remote has objects.
9. **Lockfile is generated** — commit it; resolve conflicts by re-running stages, not hand-editing hashes.
10. **Match remote extras** — missing `boto3`/GCS/Azure libs → install DVC with the right extra, don't fake success.

## Agent operating procedure

When the user asks for DVC help:

1. **Orient** — detect init state, remotes (`dvc remote list`), stages (`dvc dag` / read `dvc.yaml`), dirty status (`dvc status`, `git status`).
2. **Choose workflow** — A/B/C/D above; load [workflows.md](references/workflows.md) if multi-step.
3. **Execute real CLI** — run `dvc` / `git` commands; do not only write YAML from memory when `dvc stage add` can author it safely.
4. **Verify** — `dvc status`, `dvc repro` dry outcomes, presence of `.dvc` pointers, gitignore lines for bulk paths.
5. **Report** — what was tracked, which metafiles to commit, whether `dvc push` is still needed, any missing remote/credentials.

When only explaining (no machine changes): still follow the mental model and hard rules; cite official docs for deep flags.

## Out of scope

- Replacing Git for source code.
- Training frameworks themselves (only how DVC wraps their I/O).
- Non-DVC experiment trackers (MLflow, W&B) unless user asks to integrate with DVC.

If DVC is the wrong tool (tiny CSV already in Git, one-off script with no reuse), say so and suggest the simpler path.
